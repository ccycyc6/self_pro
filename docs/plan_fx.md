# 视觉增强 + 运动检测 —— 实施计划

> 目标：不测距，用**画质算法 + 运动检测**做一个「怎么演示都不塌」的成品
> 基线：`s3h` 位流（sha 141344AD…），双相机 + 画中画 + OSD 已在板上验证

---

## 一、最终形态

```
┌──────────────────────────────────────┬──────────────┐
│                                      │              │
│   cam1 主画面：增强后（夜视/伪彩/锐化） │  cam2 原始灰度 │
│                                      │  （对照组）    │
│        ┌────┐        ┌────┐          │              │
│        │运动│        │运动│          │              │
│        └────┘        └────┘          │              │
└──────────────────────────────────────┴──────────────┘
         NIGHT VISION          02
         ↑ 当前模式            ↑ 运动目标数
```

**为什么这个方案稳**：增强只查表、运动检测只做帧差，**都不依赖场景里有纹理、有标定、有物体**
——现场效果 100% 可复现。

---

## 二、分阶段（每阶段一个 gate）

### P0 冻结现状（0.5 h）

- 打 tag `stable-s3h`；
- 三条验证必须绿：`make yolo`（golden 0）、`make stereo-sim`、`make pip`；
- 产物归档到 `build/release/`。

**Gate**：三条全绿。

### P1 `video_fx.v`（1 h）

像素域模块，插在 **PiP 之后、OSD 之前**，只处理主画面：

| 模式 | 算法 | 实现 |
|---|---|---|
| 0 直通 | — | 直连 |
| 1 夜视 | 伽马提升 + 绿色单色 + 噪声门限 | 256 项 LUT（R/G/B 查表） |
| 2 伪彩 | 亮度 → 蓝→青→绿→黄→红 | 256 项 24 位调色板 LUT |
| 3 锐化 | 3×3 拉普拉斯 | 需要 2 行行缓存（BRAM） |

先做 0/1/2（纯 LUT，零风险），3 作为可选加细。

**Gate**：`sim/rtl/tb_video_fx.sv` 用已知输入验证三种模式的输出（像素级对照），
`VIDEO_FX TEST PASSED`。

### P2 接入 + 位流（0.5 h + 15 min）

- `video_fb_top` 里插 `video_fx`；
- MMIO `0xD000_B000`：模式寄存器（低 2 位）；
- 构建前先跑 `tools/build_pango.ps1`（它会先 prep）。

**Gate**：位流构建通过且时序不比 s3h 差。

### P3 串口切模式（0.5 h）

- 固件轮询 UART：`n`=夜视、`f`=伪彩、`o`=原始、`s`=锐化；
- 写 MMIO 模式寄存器；
- 屏幕右下角数字显示当前模式编号。

**Gate**：串口发字符，屏幕模式立刻变化。

### P4 运动检测（2 h）

- 32×32 缩略图相邻帧相减（阈值可调）；
- 连通域 → 最多 4 个框（用现成的 4 框 OSD）；
- 屏幕文字显示目标数；
- UART `t<数字>` 调阈值，便于现场适配。

**Gate**：挥手 → 框出现；静止 → 框消失。

### P5 上板验收（0.5 h）

- 三种模式截图/录屏；
- 运动框 + 目标数；
- 记录帧率（预期运动检测只占 <0.1 M 周期 → 不受影响）。

### P6 文档与提交（0.5 h）

- 更新 `docs/advanced_plan.md` 与 `docs/goals.md`；
- 归档位流 + sha256；
- 一个 gate 一个 commit + tag。

## 四、和 YOLO 的关系

这条链路是 YOLO 的**前置条件**，不是替代：

```
低照度 → [video_fx 夜视/锐化] → 32×32 → 加速器（分类器）
```

真实产品也是这么做的（先增强再检测）。所以做完 P1–P4 之后，
再把加速器接成「框内是不是目标」的分类器，成功率比之前直接检测高得多。

## 六、扩展：YOLO 跟踪 + 极简语言模型（可选阶段）

### P7 简单跟踪（在 P4 之上）

**跟踪不需要神经网络**——用我们已经有的 SAD 匹配器做「时间域模板跟踪」最省事也最稳：

```
第 N 帧：在运动框中心取 32×32 模板
第 N+1 帧：在 ±8 像素范围里找模板的最佳位移 → 新位置
         位移太大 → 认为跟丢，回到 P4 的运动检测重新捕获
```

- 计算量：32×32 模板 × 17×17 位移 ≈ 296K 次比较 ≈ 0.3 M 周期（约 11 ms）
- 32×32 可先在 2× 降采样上找，再细化 → 降到 0.1 M

**YOLO（加速器）负责“是什么”**，不负责“在哪”：

| 角色 | 谁做 |
|---|---|
| 在哪（框、位移） | SAD 模板跟踪 |
| 是什么（目标/非目标、类别） | 加速器 32×32 **分类器** |

分类器的输入就是跟踪框内的 32×32 图像，输出 2–8 类的概率。
**分类比检测容易得多**，32×32 完全够用，这是把 YOLO 真正接回链路的最低风险方式。

- 采数据：1–2 分钟录 200–400 帧（框由跟踪自动给出，自动标注）
- 训练：torch，几分钟
- 部署：只换固件（**不用重烧位流**）

**Gate**：画面里放目标 → 框跟随且标签正确；把目标拿走 → 标签变“无目标”。

### P8 极简语言模型（可选，需先确认预期）

先说算力账（这决定“能跑多大”）：

| 指标 | 数值 |
|---|---|
| 阵列峰值 | 4×4 INT8 × 27 MHz = **432 MMAC/s** |
| 实测（32×32 四层网络） | 745K MAC / 1.1M 周期 ≈ **0.7 MAC/cycle** |
| 换算 | ≈ **18 MMAC/s** 有效 |

效率低是因为小张量、DMA 与命令开销占比高；矩阵-向量（batch=1）在脉动阵列上更吃亏。

**结论**：

| 模型 | 每 token 计算量 | 速度 | 可行性 |
|---|---|---|---|
| 意图分类器（embedding 32 → 16 类） | ~5K MAC | **>1000 token/s** | ✅ **完全可行** |
| 字符级 GRU（hidden 64，≤100K 参数） | ~200K MAC | 10–50 token/s | ⚠️ 可行但慢 |
| 小型 Transformer（1M 参数） | ~2M MAC + 注意力 | <5 token/s | ❌ 不实际 |

**建议的“极简语言模型”形态**：**指令分类器 + 模板回答**

```
串口输入一句话（按词查表成 32 维向量）
      ↓ 加速器：一个 1×1 GEMM（32 → 16 类）
  意图类别（"问距离"/"问数量"/"切模式"/"打招呼"…）
      ↓
模板回答 + 实时数值（距离、目标数、模式号）→ 屏幕/串口
```

例：

| 输入 | 输出（屏幕/串口） |
|---|---|
| `dist?` | `2.14 m` |
| `count?` | `2 targets` |
| `night` | 切到夜视模式，回 `mode=1` |

这**是真的在加速器上跑推理**（GEMM），而且延迟 <1 ms，风险极低。

**若要“生成式”**：字符级 GRU（≤100K 参数、词表 64），输出 10–20 个字符需要 0.2–0.4 s，
可以演示“打一句、回一句短的”，但**别期待流畅对话**。

**Gate**：串口提问 → 1 秒内正确回答（分类器）；生成式作为加分项。
