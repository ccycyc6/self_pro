# 进阶版规划 —— 从"能跑"到"能用"

> 基线：`board-b7b`（2026-10-30）
> 底座：PG2L200H-6IFBB676 / RV32IM 单核 / miniTensor 4×4 INT8 / OV5640 / DDR3 / HDMI
> 现状：720p30 画面 + 绿框（最亮块跟踪）+ 加速器 268 ms/帧

---

## 一、最终成品定义

一块**实时多目标视觉板**，上电自启、不依赖 PC：

### 屏幕上

```
┌──────────────────────────────────────────────┐
│                                              │
│      ┌──────────┐                            │
│      │ person   │  ← 绿色框 + 类别 + 置信度   │
│      │  0.82    │     框随目标移动，多目标并列  │
│      └──────────┘                            │
│                    ┌────────┐                │
│                    │ cup    │                │
│                    │ 0.64   │                │
│                    └────────┘                │
│                                              │
└──────────────────────────────────────────────┘
       1280×720 @ 30 fps，检测 ≥ 15 fps
```

### 指标（验收线）

| 项目 | 目标 |
|---|---|
| 输入 | 摄像头 720p30，画面无撕裂 |
| 模型 | 64×64×3，4 层卷积 + 检测头，INT8 |
| 类别 | ≥ 3 类（自建小数据集） |
| 端到端 | **≥ 15 fps**（≤ 66 ms/帧） |
| 延迟 | 从曝光到框上屏 ≤ 100 ms |
| 多目标 | 同时 ≤ 4 个，NMS 后不重叠 |
| 启动 | 上电自动加载模型并开始检测（无 PC） |
| 精度 | 与 PC 端整数参考**逐比特一致** |

### 演示脚本（3 分钟）

1. 上电 → 3 秒内出画面 + 空场景无框；
2. 举起目标物 → 框出现，类别与置信度上屏；
3. 两个目标同时入镜 → 两个框；
4. 拔掉摄像头 → 自动切测试图案（不黑屏）；
5. 串口输出结构化日志（CSV 一行一个检测）。

## 二、P1 的风险评估（结论：低）

之前我把 P1 标成"中"，重新评估后**降到低**，理由是可验证性和爆炸半径都小：

| 风险来源 | 为什么低 |
|---|---|
| 功能正确性 | `make yolo` 的 golden 逐字节比对仍在，每步改完必须 diff 0，Verilator 全流程约 2 分钟 |
| 爆炸半径 | 改动全在 `mt_cluster` 内部（DMA/控制器/UB），不碰 CPU、视频、时钟、复位、引脚 |
| 时序 | 不加新时钟、不加 CDC；27 MHz 下余量 +17 ns，真不合理就退回去 |
| 上板成本 | 一次位流 28 分钟，固件 5 秒；失败一轮的代价可控 |
| 回退 | 四个子步各自独立 commit + tag，任何一步可以单独 revert |
| 已知坑 | ADS Flow-0189 的两种触发已定位（`$fatal` 块、struct 由 always_comb 驱动），新模块按规矩写即可 |

唯一真实风险是**排期**（比预期多迭代几轮），不是正确性。

## 三、计划（每关一个 commit + tag）

### P1 —— 供给链改造（3 周，功能不变、只变快）

| Gate | 内容 | 验收 |
|---|---|---|
| **P1.1** | 描述符化：CPU 写一张命令表，张量自取指令、自结束 | 命令数不变，MMIO 写 17,184 → <100；golden 0 |
| **P1.2** | DMA 乒乓双缓冲：算 tile N 时预取 N+1 | 总周期 ≤ 50% |
| **P1.3** | tile 4×4 → 8×8（同时扩 UB 4 KB → 16 KB） | 命令数 ≤ 1/3；DRM ≤ 60 |
| **P1.4** | 硬件 K 循环计数器（K 维不再由 CPU 展开） | 命令数再降；总周期 ≤ 10% |
| **出口** | —— | **现有模型 ≤ 10 ms/帧（≥ 25×）**，golden 仍 0 |

### P2 —— 真模型（3 周）

| Gate | 内容 | 验收 |
|---|---|---|
| **P2.1** | 打包器通用化（任意层拓扑 + 逐层 scale） | 打包 6 层网络，PC 参考与板端一致 |
| **P2.2** | 数据采集：板上 64×64×3 抓帧到 UART/PC，标注 300–500 张 | 数据集可用 |
| **P2.3** | PyTorch 训练 + INT8 量化 + 导出 | PC 端 mAP/召回达到设定值 |
| **P2.4** | 板上对齐 | 与 PC 整数参考逐比特一致 |
| **出口** | —— | 单类别识别正确率 ≥ 80%，**≤ 66 ms/帧（≥ 15 fps）** |

### P3 —— 产品化输出（2 周）

| Gate | 内容 | 验收 |
|---|---|---|
| **P3.1** | 8×8 点阵字体 ROM（~1 KB）+ OSD 文字层 | 屏幕上能显示类别与数值 |
| **P3.2** | 多目标 + NMS（CPU 上 C 实现） | ≤ 4 目标，框不重叠 |
| **P3.3** | UART 结构化日志 + LED 状态码 | PC 端一行解析 |
| **出口** | —— | 演示脚本 3 分钟全程无人工干预 |

### P4 —— 可选（有窗口期再做）

| 项 | 价值 | 备注 |
|---|---|---|
| SPI Flash 存模型、上电自启 | 摆脱 PC | 需 3–5 天 |
| DDR3 作为 DMA 第二主口 | 大模型/多帧 | 需仲裁器，风险最高 |
| 27 → 50 MHz | ×1.8 | 时序重收敛，1 天 |
| 8×8 阵列 | ×4 | 需重做数据通路，2 周 |

## 四、排期

```
周 1–3   P1.1 → P1.4      出口：现有模型 ≤10 ms/帧
周 4     P2.1 + P2.2      出口：数据集 + 打包器
周 5     P2.3              出口：PC 端模型达标
周 6     P2.4              出口：板上逐比特一致
周 7–8   P3.1 → P3.3      出口：成品演示
```

每个 Gate 结束都：`make yolo` diff 0 → 位流 → 上板 → 记录 → commit + tag。

---

## 五、明确不做

1. **不换大模型**（416×416 YOLO）：DDR3 带宽与 UB 都不够，先把 64×64 做扎实；
2. **不先上 8×8 阵列**：现在差 106 倍的不是算力，是供给；
3. **不在模型真训练前做 OSD 文字**：会把随机数打上屏，比没有更糟；
4. **不引入 MMU/OS**：演示板不需要，收益低风险高。

## 六、当前差距一览（P1 的靶子）

```
每帧周期   7,264,264     @27 MHz = 268 ms
命令数     17,184
每命令     422 周期
MAC 总量   ≈1.10 M
理想下限   68,750 周期（16 MAC/cycle）
差距       106×
```

P1 的目标就是把"106×"打下来，而不是加算力。

## 七、P1 的第一手测量（仿真，2026-10-30）

在 `mt_cluster` 里加了两个自由运行的计数器，通过 MT 窗口暴露：

| 地址 | 内容 |
|---|---|
| `0xE000_0018` | DMA 反压周期（`mem_rd/wr_valid && !ready`） |
| `0xE000_001C` | cluster 忙周期（status[0]） |

`make yolo` 实测（golden 仍为 0）：

    total     = 7,267,573 周期
    busy      =   558,506  (7.7%)
    dma_stall =     1,344  (0.02%)

**结论：加速器只有 7.7% 的时间在忙，DMA 几乎不等待——92% 的帧时间花在 CPU
逐条写命令上（17,184 条 × 约 390 周期）。**

所以 P1.1（描述符化）的收益上限约 **10 倍**，而且不碰数据通路、不碰时序。

## 八、P1a：软件侧（2026-10-30 01:20）

两项纯软件改动，逐字节一致：

| 改动 | 效果 |
|---|---|
| tap 解码（两次除法）从每个 (tap,tile) 提到每个 tap | 除法次数 ÷16 |
| UB_A 四行 + 相邻 tile 连续 → 一次 DMA 装 4 个 tile 的 A | LOAD 命令 ÷4 |

     命令数   17,184 -> 14,272   (-17%)
     周期数 7,267,573 -> 6,216,376  (-14.5%)
     golden diff 0 bytes

## 九、P1b：GEMM 突发引擎（2026-10-30 02:06，板上验证）

指令的 rd 字段（原本未用）改为重复次数，shim 在每次 result 之后把 rs1/rs2 加上
`MT_BSTEP` 里的行步长再发一次，只有最后一次才置 DONE。

| 版本 | 位流 sha256 | 帧周期 | 命令数 |
|---|---|---|---|
| B7b 基线 | `8CE41766…` | 7,168,xxx | 17,184 |
| P1a 软件 | `8CE41766…` | 6,216,376（仿真） | 14,272 |
| **P1b 突发** | `6B88D688…` | **4,853,047（板上）** | 6,720 |

板上串口实测：

    net: cell=(3,3) t=4853047
    f=287 bright=(5,2) box=(720,200)-(800,280) luma=192/118

绿框仍在跟踪，说明突发引擎没有破坏功能。

## 十、P1c：epilogue / vector 突发（2026-10-30 02:30）

第一次尝试失败（golden 差 38 字节），原因是 **MT_BSTEP 被 epilogue 改成 (4,0,1)
之后没有复位，下一行的 GEMM 突发沿用了错误步长**。修法：每个 tap 开始时重新装载。

| 版本 | 命令数 | 周期 | 备注 |
|---|---|---|---|
| P1b | 6,720 | 4,984,594 | 板上验证 |
| P1c | 6,032 | 4,921,025 | 仿真验证，golden 0 |

玩具网络没有 leaky/skip 层，vector 突发暂时不减少命令数，是为深模型准备的。

## 十一、剩余瓶颈与下一步

4.92 M 周期里约 76% 是**外层循环的控制与地址运算**（每个 push 摊到约 800 周期），
不是 push 本身，也不是阵列、不是 DMA。

要再上一个数量级，只有一条路：把 `ho × tc × q × tile-group` 这层循环搬进硬件——
即真正的层描述符引擎（P2 的第一件事）。
**P1c 上板实测（2026-10-30 02:41，位流 `4273417A…`）**

    net: cell=(3,3) t=4807535 busy=519154 dma_stall=1293
    f=285 bright=(5,2) box=(720,200)-(800,280) luma=192/117

| 版本 | 位流 sha256 | 板上帧周期 | 相对基线 |
|---|---|---|---|
| B7b 基线 | `8CE41766…` | 7,168,xxx | — |
| P1b GEMM 突发 | `6B88D688…` | 4,853,047 | −32% |
| **P1c + epilogue/vector** | `4273417A…` | **4,807,535** | **−33%** |

绿框仍正常跟踪（`bright=(5,2)`、坐标稳定），说明突发引擎在真实数据上无误。

## 十二、P1d：两次"廉价"优化，帧时间从 4.81 M 掉到 2.00 M

用 `MT_PROF` 把 net_pad / net_pool 也计了时，发现**真正的瓶颈根本不在加速器**：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| net_pad（逐字节 + 内层边界判断） | ~3.6 M | 词宽拷贝 + 行拆三段 |
| net_pool_k（4 个通道各算一次完整地址） | ~0.9 M | 按像素取 32 位字、按字节取最大 |

| 版本 | 帧周期 | golden |
|---|---|---|
| P1c（突发引擎） | 4,807,535（板上） | 0 |
| + net_pad 词宽化 | 2,632,453 | 0 |
| + 池化按像素 | **1,995,627** | 0 |

累计相对 B7b 基线（7,168,xxx）：**−72%**；加速器占用从 8% 升到 **26%**。

**教训**：先测量再优化，两次改动都只有几十行 C，收益却超过前面所有 RTL 工作之和。
下一轮如果还要提速，先看 `MT_PROF` 的 six-phase 分解，不要凭直觉动 RTL。

## 十三、P1e / P1f：队列加深 + 二维突发（2026-10-30 10:30）

| Gate | 改动 | 命令数 | 周期 | golden |
|---|---|---|---|---|
| P1d | pad / pool 词宽化（纯 C） | 6,032 | 1,995,627 | 0 |
| P1e | 命令队列 8 -> 64 深（RTL） | 6,032 | 1,868,033 | 0 |
| **P1f** | **二维 GEMM 突发（RTL）** | **3,120** | **1,424,779** | **0** |

相对 B7b 基线（7,168,xxx）：**−80%**；加速器占用 36%。

**P1f 的设计**：卷积最内层是 u x j 二维网格——u 走 tile 列（A 行 +1、C 行 +4），
j 走一列内的输出组（权重行 +1、C 行 +ntiles4）。一维突发表达不了，所以 shim 增加了
第二对计数器和一个 0x09 的宏指令：

- 形状 (nu, nj) 放在指令里未用的 rs1/rs2 字段（**不能放进 rs1 的高 16 位**：
  张量会检查 `rs1[31:16] == 0`，放进去就被判非法——这是踩过的坑）；
- `MT_BSTEP` 增加第四字节（内层 C 行步长）；
- shim 把宏翻译成普通 0x05 GEMM，张量永远只看到它认识的指令。

**踩坑记录**：内层步长最初只改了权重行、忘了 C 行，结果 golden 差 30 字节；
补上 `d_step` 后逐字节一致。
**P1f 位流（2026-10-30 10:54）**

    build/pango/p1f/generate_bitstream/video_fb_top.sbit
    sha256 71BC1C0F8909E515DC5F262D2D0ABF49DFD40BB89621B25A141A98BD20F8102D
    LUT 25,760 (16.1%)   REG 14,860   DRM 52/415   hold 边角 -0.071 ns

上板验证时 JTAG 链返回 `No devices detected`（板子当时未上电），待上电后补测。

## 十四、P1f 上板验证 + 一次失败的合并（2026-10-30 11:10）

板上实测（p1f 位流 `71BC1C0F…`）：

     net: cell=(3,3) t=1296250 busy=515743 dma_stall=1275
    f=3981 bright=(5,2) box=(720,200)-(800,280) luma=208/104

**1,296,250 周期 = 48 ms/帧 ≈ 21 帧/秒**，绿框稳定。

| 版本 | 板上帧周期 | 相对 B7b |
|---|---|---|
| B7b | 7,168,xxx | — |
| P1d | —（仿真 2.0M） | |
| P1f | **1,296,250** | **−82%** |

### 失败的尝试：把 LOAD 和二维突发合并成一条命令

想法：卷积每处理 4 个 tile 要发一条 LOAD 和一条二维突发，合成一条可再省 40% 命令。

做法已实现（队列项加宽到 168 位、加 `0x0A` 宏、shim 先发 LOAD 再发网格），
但张量始终回 `result_err`（status `0x00000006`），而 issue/commit 阶段的
`operands_valid` 检查都通过。原因未定位，**已整体回滚**，代码回到 p1f 状态。

**教训**：宏指令跨两层（shim 翻译 + 张量校验）时，出错点会被藏在
"操作数在路上被改写"这类细节里；下次应该先做一个最小可复现的单元测试
（单条 LOAD、单条 2D、单条 LOAD+2D），而不是直接上整网。

## 十五、P1g / P1h：合并 LOAD 与突发、改成"满才等"（2026-10-30 11:40）

| Gate | 改动 | 命令数 | 周期 | golden |
|---|---|---|---|---|
| P1f | 二维突发（板上 1,296,250） | 3,120 | 1,405,748 | 0 |
| P1g | LOAD 与二维突发合成一条（0x0A） | 1,936 | 1,353,157 | 0 |
| **P1h** | 状态字加 FULL 位，推送"满才等" | 1,936 | **1,230,474** | 0 |

相对 B7b 基线（7,168,xxx）：**−83%**；加速器占用 41%。

**单元测试救了这一轮**：上一次 0x0A 失败后回滚，这次先写了三条指令的单元测试
（`-DMT_UNITTEST`：单条 LOAD、单条 GEMM2D、单条合并命令），三条全过，
整网随之通过。教训兑现：**宏指令先做最小可复现测试**。

**还有一个测出来的事实**：一次 4 次 MMIO 存储的完整命令约 30 周期（7.5/次），
所以"写命令"本身很便宜——真正的开销在等待与协议往返，而不是 store 指令。
**P1h 上板（2026-10-30 11:49，位流 `5CDD2416…`，LUT 25,836 / DRM 53）**

    net: cell=(3,3) t=1102545 busy=513860 dma_stall=915

**1,102,545 周期 = 41 ms/帧 ≈ 24 帧/秒**，加速器占用 **47%**。
