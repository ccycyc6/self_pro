# 进阶版规划 —— 从"能跑"到"能用"

> 基线：`board-b7b`（2026-10-30）
> 底座：PG2L200H-6IFBB676 / RV32IM 单核 / miniTensor 4×4 INT8 / OV5640 / DDR3 / HDMI
> 现状：720p30 画面 + 绿框（最亮块跟踪）+ 加速器 268 ms/帧

---

## 一、最终成品定义

一块**实时多目标视觉板**，上电自启、不依赖 PC：

### 屏幕上

```
┌──────────────────────────────────────────────┐
│                                              │
│      ┌──────────┐                            │
│      │ person   │  ← 绿色框 + 类别 + 置信度   │
│      │  0.82    │     框随目标移动，多目标并列  │
│      └──────────┘                            │
│                    ┌────────┐                │
│                    │ cup    │                │
│                    │ 0.64   │                │
│                    └────────┘                │
│                                              │
└──────────────────────────────────────────────┘
       1280×720 @ 30 fps，检测 ≥ 15 fps
```

### 指标（验收线）

| 项目 | 目标 |
|---|---|
| 输入 | 摄像头 720p30，画面无撕裂 |
| 模型 | 64×64×3，4 层卷积 + 检测头，INT8 |
| 类别 | ≥ 3 类（自建小数据集） |
| 端到端 | **≥ 15 fps**（≤ 66 ms/帧） |
| 延迟 | 从曝光到框上屏 ≤ 100 ms |
| 多目标 | 同时 ≤ 4 个，NMS 后不重叠 |
| 启动 | 上电自动加载模型并开始检测（无 PC） |
| 精度 | 与 PC 端整数参考**逐比特一致** |

### 演示脚本（3 分钟）

1. 上电 → 3 秒内出画面 + 空场景无框；
2. 举起目标物 → 框出现，类别与置信度上屏；
3. 两个目标同时入镜 → 两个框；
4. 拔掉摄像头 → 自动切测试图案（不黑屏）；
5. 串口输出结构化日志（CSV 一行一个检测）。

## 二、P1 的风险评估（结论：低）

之前我把 P1 标成"中"，重新评估后**降到低**，理由是可验证性和爆炸半径都小：

| 风险来源 | 为什么低 |
|---|---|
| 功能正确性 | `make yolo` 的 golden 逐字节比对仍在，每步改完必须 diff 0，Verilator 全流程约 2 分钟 |
| 爆炸半径 | 改动全在 `mt_cluster` 内部（DMA/控制器/UB），不碰 CPU、视频、时钟、复位、引脚 |
| 时序 | 不加新时钟、不加 CDC；27 MHz 下余量 +17 ns，真不合理就退回去 |
| 上板成本 | 一次位流 28 分钟，固件 5 秒；失败一轮的代价可控 |
| 回退 | 四个子步各自独立 commit + tag，任何一步可以单独 revert |
| 已知坑 | ADS Flow-0189 的两种触发已定位（`$fatal` 块、struct 由 always_comb 驱动），新模块按规矩写即可 |

唯一真实风险是**排期**（比预期多迭代几轮），不是正确性。

## 三、计划（每关一个 commit + tag）

### P1 —— 供给链改造（3 周，功能不变、只变快）

| Gate | 内容 | 验收 |
|---|---|---|
| **P1.1** | 描述符化：CPU 写一张命令表，张量自取指令、自结束 | 命令数不变，MMIO 写 17,184 → <100；golden 0 |
| **P1.2** | DMA 乒乓双缓冲：算 tile N 时预取 N+1 | 总周期 ≤ 50% |
| **P1.3** | tile 4×4 → 8×8（同时扩 UB 4 KB → 16 KB） | 命令数 ≤ 1/3；DRM ≤ 60 |
| **P1.4** | 硬件 K 循环计数器（K 维不再由 CPU 展开） | 命令数再降；总周期 ≤ 10% |
| **出口** | —— | **现有模型 ≤ 10 ms/帧（≥ 25×）**，golden 仍 0 |

### P2 —— 真模型（3 周）

| Gate | 内容 | 验收 |
|---|---|---|
| **P2.1** | 打包器通用化（任意层拓扑 + 逐层 scale） | 打包 6 层网络，PC 参考与板端一致 |
| **P2.2** | 数据采集：板上 64×64×3 抓帧到 UART/PC，标注 300–500 张 | 数据集可用 |
| **P2.3** | PyTorch 训练 + INT8 量化 + 导出 | PC 端 mAP/召回达到设定值 |
| **P2.4** | 板上对齐 | 与 PC 整数参考逐比特一致 |
| **出口** | —— | 单类别识别正确率 ≥ 80%，**≤ 66 ms/帧（≥ 15 fps）** |

### P3 —— 产品化输出（2 周）

| Gate | 内容 | 验收 |
|---|---|---|
| **P3.1** | 8×8 点阵字体 ROM（~1 KB）+ OSD 文字层 | 屏幕上能显示类别与数值 |
| **P3.2** | 多目标 + NMS（CPU 上 C 实现） | ≤ 4 目标，框不重叠 |
| **P3.3** | UART 结构化日志 + LED 状态码 | PC 端一行解析 |
| **出口** | —— | 演示脚本 3 分钟全程无人工干预 |

### P4 —— 可选（有窗口期再做）

| 项 | 价值 | 备注 |
|---|---|---|
| SPI Flash 存模型、上电自启 | 摆脱 PC | 需 3–5 天 |
| DDR3 作为 DMA 第二主口 | 大模型/多帧 | 需仲裁器，风险最高 |
| 27 → 50 MHz | ×1.8 | 时序重收敛，1 天 |
| 8×8 阵列 | ×4 | 需重做数据通路，2 周 |

## 四、排期

```
周 1–3   P1.1 → P1.4      出口：现有模型 ≤10 ms/帧
周 4     P2.1 + P2.2      出口：数据集 + 打包器
周 5     P2.3              出口：PC 端模型达标
周 6     P2.4              出口：板上逐比特一致
周 7–8   P3.1 → P3.3      出口：成品演示
```

每个 Gate 结束都：`make yolo` diff 0 → 位流 → 上板 → 记录 → commit + tag。

## 五、明确不做

1. **不换大模型**（416×416 YOLO）：DDR3 带宽与 UB 都不够，先把 64×64 做扎实；
2. **不先上 8×8 阵列**：现在差 106 倍的不是算力，是供给；
3. **不在模型真训练前做 OSD 文字**：会把随机数打上屏，比没有更糟；
4. **不引入 MMU/OS**：演示板不需要，收益低风险高。

## 七、P1 的第一手测量（仿真，2026-10-30）

在 `mt_cluster` 里加了两个自由运行的计数器，通过 MT 窗口暴露：

| 地址 | 内容 |
|---|---|
| `0xE000_0018` | DMA 反压周期（`mem_rd/wr_valid && !ready`） |
| `0xE000_001C` | cluster 忙周期（status[0]） |

`make yolo` 实测（golden 仍为 0）：

    total     = 7,267,573 周期
    busy      =   558,506  (7.7%)
    dma_stall =     1,344  (0.02%)

**结论：加速器只有 7.7% 的时间在忙，DMA 几乎不等待——92% 的帧时间花在 CPU
逐条写命令上（17,184 条 × 约 390 周期）。**

所以 P1.1（描述符化）的收益上限约 **10 倍**，而且不碰数据通路、不碰时序。

## 十一、剩余瓶颈与下一步

4.92 M 周期里约 76% 是**外层循环的控制与地址运算**（每个 push 摊到约 800 周期），
不是 push 本身，也不是阵列、不是 DMA。

要再上一个数量级，只有一条路：把 `ho × tc × q × tile-group` 这层循环搬进硬件——
即真正的层描述符引擎（P2 的第一件事）。

## 十二、P1d：两次"廉价"优化，帧时间从 4.81 M 掉到 2.00 M

| 版本 | 帧周期 | golden |
|---|---|---|
| P1c（突发引擎） | 4,807,535（板上） | 0 |

## 十三、P1e / P1f：队列加深 + 二维突发（2026-10-30 10:30）

| Gate | 改动 | 命令数 | 周期 | golden |
|---|---|---|---|---|
| P1d | pad / pool 词宽化（纯 C） | 6,032 | 1,995,627 | 0 |
| P1e | 命令队列 8 -> 64 深（RTL） | 6,032 | 1,868,033 | 0 |
| **P1f** | **二维 GEMM 突发（RTL）** | **3,120** | **1,424,779** | **0** |

相对 B7b 基线（7,168,xxx）：**−80%**；加速器占用 36%。

**P1f 的设计**：卷积最内层是 u x j 二维网格——u 走 tile 列（A 行 +1、C 行 +4），
j 走一列内的输出组（权重行 +1、C 行 +ntiles4）。一维突发表达不了，所以 shim 增加了
第二对计数器和一个 0x09 的宏指令：

- 形状 (nu, nj) 放在指令里未用的 rs1/rs2 字段（**不能放进 rs1 的高 16 位**：
  张量会检查 `rs1[31:16] == 0`，放进去就被判非法——这是踩过的坑）；
- `MT_BSTEP` 增加第四字节（内层 C 行步长）；
- shim 把宏翻译成普通 0x05 GEMM，张量永远只看到它认识的指令。

**踩坑记录**：内层步长最初只改了权重行、忘了 C 行，结果 golden 差 30 字节；
补上 `d_step` 后逐字节一致。

## 十六、下一步设计：命令表回放（P2.1，尚未实现）

### 目标

每帧只写 2 条 MMIO，硬件自己把整帧的命令喂进去；帧时间从 1.10 M 掉到 ~0.55 M（约 20 ms/帧）。

### 为什么不是"把表放进 4 KB 窗口"

MT 窗口只有 4 KB（`addr[31:12] == MT_BASE[31:12]`），一帧 1,936 条 × 168 位 ≈ 40 KB，
塞不进去；而且每帧重新填表等于没省。表必须**放在 scratch 里、只建一次**。

### 结构

```
scratch (0x1000_0000)
   └── 命令表：N × 168 位，启动时由 CPU 建好（一次性，约 12 K 次 store）
        │
        ▼  mt_cmd_fetch（新增，在 mt_cluster 内）
   mem_rd_*  ──►  mt_dma_l2_bridge  ──►  L2
        │
        ▼
   现有 mt_cmd_fifo ──► mt_cvxif_shim（不改）
```

### 关键点

1. **端口仲裁**：fetch 只在"张量没有未完成请求"时占用 `mem_rd_*`：
   `outstanding = mem_rd_valid && mem_rd_ready` 置位、`mem_rsp_valid` 清零。
   fetch 拿到端口后占用一个完整往返，不会偷走张量的响应。
2. **只做单条 64 位读**：表项 168 位 = 3 个 64 位（或 6 个 32 位）读，fetch 组装后推进 FIFO。
   更省事的做法是**把表项缩到 64 位**：只存 {instr[31:0], rs1[15:0], rs2[15:0]}，
   把 8 位的步长和形状改成"每条命令自带"或"按段设置"，表就变成 8 字节/条 = 15 KB。
3. **完成判定**：`count == 0 && fifo_empty && shim idle` → 置 DONE，CPU 只需轮询一次。
4. **回退开关**：固件保留现有 push 路径，用 `MT_REPLAY` 宏切换；RTL 是纯新增，
   失败时固件切回即可，不必重烧。

### 验收

| 项 | 目标 |
|---|---|
| 功能 | `make yolo` golden 0 |
| 帧周期 | ≤ 700 K（1.6× 以上） |
| MMIO 写次数/帧 | ≤ 8 |
| 资源 | DRM ≤ 60，LUT ≤ 28 K |

### 风险

- fetch 与 DMA 抢同一个 L2 端口 → 仲裁错误会让张量丢响应；**必须先写单条读取的单元测试**；
- 表项格式一旦定下，固件与 RTL 要同步改，建议先用 64 位表项把流程跑通。

## 十七、P2 前置实验：能不能让"玩具模型"学会挑颜色？（2026-10-30 14:40，结论：不能）

动机：不换训练框架、不改 RTL，只把合成任务从"找最亮块"改成"找红色块"，
就能让演示从"跟着灯跑"升级成"跟着红球跑"。

做法与结果（都是 `tools/model/train_detector.py` 的变体）：

| 变体 | 质心误差 | 3px 内命中 |
|---|---|---|
| 原任务（找白方块，灰度） | **0.95 px** | **100%** |
| 彩色任务 + 随机卷积核 | 3.27 px | 44% |
| 彩色任务 + 单个干扰块 | 3.28 px | 48% |
| 彩色任务 + 无彩色干扰（只有白/灰） | 2.82 px | 65% |
| 彩色任务 + **手工设计颜色对抗核** | 2.85 px | 63% |
| 彩色任务 + 干扰块不遮挡 + 设计核 | 2.93 px | 60% |

**结论**：在"固定特征 + 线性头"这个框架里，**挑颜色做不到可靠**。
即使把第一层换成颜色对抗核（R−G/2−B/2，对白/灰输出恰为 0），线性头仍会被
干扰块的**边缘特征**拉偏质心（固定卷积 + ReLU + 池化之后，边缘响应无法被线性地
完全抑制）。

**这意味着 P2 必须换训练方式**：
- 需要真正的反向传播（整网训练），而不是最小二乘只训头；
- 本机 WSL 只有 numpy 1.26.4，**没有 torch**：要么离线装 torch，要么用 numpy 手写
  一个小 CNN 的反向传播（4 层、通道 8–32，CPU 上可训练）；
- 量化-打包链路（`pack_weights.py`）不需要改：它按逐层 scale 打包任意权重。

**已回滚**：实验分支全部撤销，模型与权重恢复到 0.95 px / 100% 的版本，
`make yolo` 仍 `golden diff 0`（1,230,474 周期）。

## 十九、P2 突破：整网反向传播训练（2026-10-30 15:35）

用 numpy 手写了这个小 CNN 的反向传播（`tools/model/train_bp.py`，无 torch）：

    conv3x3 4->8  ReLU   pool2
    conv3x3 8->16 ReLU   pool2
    conv3x3 16->16 ReLU
    conv1x1 16->8        (obj, w, h)

30 个 epoch、1500 张合成图（红色目标 + 彩色/灰白干扰块）：

| 指标 | 固定随机特征 + 线性头 | **整网反传** |
|---|---|---|
| 浮点质心误差 | 2.8–3.3 px | **0.36 px** |
| 3px 内命中 | 44–65% | **100%** |
| INT8 量化后 | — | **1.24 px / 87.5%** |

**两个打包环节的坑**（都已修）：
1. `pack_weights.py` 把卷积偏置硬编码成 0——训练出来的 b1/b2/b3 会被丢掉；
2. 输入量化 scale 硬编码成 `1/127`（假定输入 0..1），一旦标定图是 0..255 字节，
   整层量化全错（实测量化后 99 px 完全失效）。改成从标定数据实测。

板上实测（p2a 位流 + 新固件）：

    net: cell=(5,3) t=1101221      ← 模型输出，稳定
    f=218 bright=(6,1) luma=207/140 ← 亮度跟踪器，跳动

绿框现在由**模型**驱动，亮度跟踪器只留在串口做对照。
