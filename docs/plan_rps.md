# 剪刀石头布（双手识别）—— 可行性评估与方案

> 基于现有硬件：双 OV5640 + miniTensor（4 层 INT8 CNN）+ RV32 + OSD
> 依赖已有的运动跟踪（M1 已通过 5 项单元测试）

---

## 一、结论：可行，属于“中等风险但回报高”的方案

| 环节 | 难度 | 说明 |
|---|---|---|
| 找到两只手 | ✅ 已有 | 运动检测 + 跟踪，最多 4 个目标 |
| 把手裁出来 | ✅ 简单 | 跟踪框 → 归一化到 32×32（**按框大小重采样**，与远近无关） |
| 识别手势 | ⚠️ **主要风险** | 3 类（石头/布/剪刀）在 32×32 灰度上靠**轮廓**区分，需要真实数据训练 |
| 判断输赢 | ✅ 平凡 | 三行查表 |
| 显示 | ⚠️ 小改动 | 现在的字体只有数字，要显示 R/P/S 需扩展字模（**随下次位流一起做**） |

**为什么比之前的“识别物品”靠谱**：手势是**三类别分类**，而且三者的轮廓差异（一个团、一张开、两根突出）
正是 32×32 能表达的特征；不像“任意物品检测”需要更强的表征。

---

## 二、三个必须处理的设计点

### ① 手停下后框会消失（关键）

现在的跟踪是**运动驱动**：手不动就没有帧差，框 5 帧后消失。
但石头石头布的姿势**恰恰是静止展示**的。

**解法：跟踪保持（hold）**

```
确认的 track → 即使在静止帧也保持 N=60 帧（约 1 秒）
             期间持续做分类（每帧一次）
             超时或被新的运动打断 → 释放
```

### ② 手和镜头距离会变（关键）

如果直接取固定大小 32×32，手近了就“撑满”、远了就“很小”，分类器会崩。

**解法：按跟踪框归一化**

```
以 track 的框（含 20% 边距）为源区域
双线性/最近邻重采样到 32×32
→ 分类器看到的手总是"填满画面"的，与距离无关
```

### ③ 两只手要算两次推理（性能）

| 项 | 数值 |
|---|---|
| 单次 32×32×4 通道推理（现有网络） | 1.1 M 周期 = 41 ms |
| 改成 32×32×**1** 通道（灰度） | 约 **0.6 M** = 22 ms |
| 两只手 | 1.2 M + 跟踪 0.43 M ≈ **1.6 M** = 60 ms → **16 fps** |

16 fps 对“摆姿势识别”够用。若不够，可把输入降到 24×24（再快 40%）。

---

## 三、方案设计

```
每帧：
  1. 运动检测 + 跟踪（已有）        → 最多 2 只手（框 + ID）
  2. 每只手的框 → 归一化 32×32 灰度
  3. 加速器推理 ×2                  → {石头, 布, 剪刀, 无}
  4. 置信度低于阈值 → 显示"?"（宁可不报）
  5. 两只手都有结果 → 查表判输赢
  6. 屏幕：框 + 类别编号；串口：手势名 + 置信度 + 胜负
```

**显示方案（分两步）**：

- **第一步（不用重新烧写位流）**：用数字表示 —— `1`=石头 `2`=布 `3`=剪刀，屏幕左下角显示 `1 3`（左手石头、右手剪刀），胜负用串口文字；
- **第二步（随 video_fx 位流一起）**：扩展字模加 `R P S` 三个字母，屏幕上直接显示 `R  S`。

## 四、分阶段（在 plan_track.md 的 M2/M3/M4 基础上细化）

| 阶段 | 内容 | 时间 | 风险 |
|---|---|---|---|
| **R1 跟踪保持** | 静止保持 60 帧；框归一化取样 | 0.5 天 | 低 |
| **R2 采集** | 串口回传归一化后的 32×32；**每类 150–200 帧**（共 600 帧，约 3 分钟） | 0.5 天 | 低 |
| **R3 训练** | torch 3 分类；数据增强（平移/亮度/随机遮挡） | 1 天 | **中**（唯一未知） |
| **R4 部署** | 双手各推理一次 + 三行胜负表 | 0.5 天 | 低 |
| **R5 演示** | 双人出拳，屏幕判定 | 0.5 天 | 低 |
| 合计 | | **约 3 天** | 零位流（R4 之前） |

## 五、风险与保底

| 风险 | 概率 | 保底方案 |
|---|---|---|
| 3 类准确率 < 70% | 中 | 降到 2 类（石头 vs 布），仍然可演示 |
| 双手同时跟踪不稳 | 低 | 先单手演示，再扩展 |
| 16 fps 不够流畅 | 低 | 输入降到 24×24，或每帧只推理一只手（交替） |
| 光照变化影响 | 中 | 采集时覆盖多种光照；推理前做归一化（减去均值） |

**最坏情况**：跟踪 + 计数演示（已通过测试），仍然是一个完整可交付的成品。

---

## 六、我的建议

**值得做**，而且优先级可以排在“通用物品识别”之前——因为：
1. 三类别、轮廓差异大，是 32×32 的“甜点问题”；
2. 演示效果强（双人出拳，屏幕判定），观众一看就懂；
3. 依赖的跟踪模块**已经完成并有测试覆盖**；
4. 失败也能降级成 2 类或纯跟踪演示。

**唯一必须先做的**：R1 的“跟踪保持”和“框归一化”——这两件事做完，采集到的数据才有意义。

# 结果（2026-11-01 02:45）

**可用**：屏幕中央偏左有一个取景框，把手掌放进去，串口每秒输出一次识别结果。

```
hand: rock     scores  11 -15   0  margin 11  shown rock
hand: paper    scores -31  26   8  margin 41  shown paper
hand: scissors scores  -2  -4   4  margin  6  shown scissors
hand: none     (window 148..164, no contrast)
```

## 最终架构

```
cam1 (720p) ──► stereo_cap（取中心 640x480，2:1 降采样）──► 0xD010_0000
                                                              │
固件：固定取景区（网格 16,14，11x9）──► letterbox 32x32 ──► 量化 ──► 加速器四层网络
                                                              │
                                     每帧一次 argmax + 裕度门限(4) + 连续 3 帧一致
                                                              │
                                                        串口 1 Hz
```

## 这一晚真正找到的五个 bug

| # | 现象 | 根因 |
|---|---|---|
| 1 | 三个手势的分数完全一样 | 补丁按 0..255 原始字节喂进 int8 引擎，>127 变成负数 |
| 2 | 板端数值与离线不符 | 相机固件里复制了一份推理序列；移到 mt_detect.c（已被 golden 验证的那份）后一致 |
| 3 | 数字卡住不动 | 裕度循环从 best=0 起、先和自己比，**第 0 类获胜时裕度恒为 0**，门限永不通过 |
| 4 | 绿框与取景区错位 40 px | 竖直偏移写成 80，正确是 120（crop 在 720p 中居中的位置） |
| 5 | 剪刀一直 weak | 剪刀通道 std 仅 0.8（靠其他两类变低来判），裕度天生 ~6，门限 8 永远过不去 |

## 验证过的数字

| 项 | 结果 |
|---|---|
| 打包后 INT8 模型在 287 张捕获补丁上 | **100%** |
